# Research: Mutation Report Analysis & Guard Detection

**Feature**: 046-survivor-mutant-tests | **Date**: 2026-08-10

## 1. Mutation Report Format

### Decision
Parse `mutants/mutmut-cicd-results.log` as a mutmut `--show-diff` unified diff report.

### Rationale
The file is a concatenation of unified diffs generated by `mutmut results --show-diff`. Each survivor entry follows this structure:

```
# <module>.xǁ<Class>ǁ<function>__mutmut_<N>: survived
--- <source_file>
+++ <source_file>
@@ -<old_start>,<old_count> +<new_start>,<new_count> @@
 <context line>
-<original line>
+<mutated line>
 <context line>
```

Entries are separated by blank lines or the next `# ` header. The `xǁ` delimiter separates the fully-qualified module path from the class-method-mutation identifier.

### Alternatives Considered
- **JSON output mode**: mutmut supports `--json` but the provided log is in diff format. Re-generating in JSON would require running mutmut (forbidden by FR-006).
- **Custom regex per mutation type**: Too fragile; the unified diff is a stable, well-defined format.

### Key Observations
| Property | Value |
|----------|-------|
| Total lines | 102,735 |
| Survivor count | 8,822 |
| Unique source files | 157 |
| Unique modules (by `xǁ` prefix) | ~50-60 |
| Entry separator | Next `# ` header line |
| Mutation ID format | `__mutmut_<N>` |

## 2. Guard Detection via Static Analysis

### Decision
Use **diff-contextual analysis**: for each survivor, identify the mutated source line and the function containing it, then check whether existing tests in `tests/` exercise that function with assertions on the mutated behavior.

### Rationale
Running `mutmut` is forbidden (FR-006). Applying mutations dynamically (patching source, running tests) would be complex and risk side effects. Static analysis based on:
1. **Diff inspection**: Extract the affected function/method from the diff header (`@@ -line,count +line,count @@`) and `---`/`+++` file paths.
2. **Test search**: Find the corresponding test file at `tests/<mirror-path>/test_<module>.py`.
3. **Coverage check**: Scan the test file for test functions that call the mutated function and assert on its return value or side effects that the mutation would alter.

### Detection Heuristics
| Mutation Type | Detection Strategy |
|---------------|-------------------|
| Operator change (`>` → `>=`, `<` → `<=`) | Check if tests assert on the boundary value specifically |
| Default value change (`{}` → `None`, `0` → `1`) | Check if tests call with the default-omitted argument |
| String literal change (`""` → `"XXXX"`, `""` → `None`) | Check if tests assert on the exact string output |
| Control flow change (`continue` → `break`) | Check if tests exercise the specific loop iteration path |
| Constant change (`0` → `1`, `999` → `1000`) | Check if tests exercise the exact input value that hits the constant |

### Alternatives Considered
- **Dynamic patching**: Apply the diff, run tests. Rejected: creates temporary source mutations, risks file corruption, and is harder to batch.
- **AST-based analysis**: Parse the Python AST and compare to the diff. Rejected: over-engineered for the task; regex-based diff analysis on the mutation line is sufficient.
- **Coverage-tool integration**: Run `pytest --cov` to get line coverage. Considered as supplement: if a source line has zero coverage, it's automatically unguarded.

## 3. Equivalent Mutant Identification

### Decision
Apply **static heuristics** to flag likely equivalent mutants, then document them in the report for human review. Do not write tests for flagged equivalents.

### Rationale
Certain mutation types rarely change observable behavior:
- **Log-statement string changes**: Mutations in `logger.info("...", key="value")` only matter if a test captures and inspects log output. Most survivors of this type will be equivalent if no log-capture test exists.
- **Type annotation mutations**: Mutations in type annotations (`dict[str, Any]` → `dict[str, str]`) have no runtime effect in Python.
- **Unreachable branch mutations**: Mutations in `if False:` blocks or dead code.
- **Default-value-only mutations**: `r.get("key", {})` → `r.get("key", None)` where the value is only used as a dict — both `{}` and `None` would cause the same downstream error.

### Heuristic Rules
| Rule | Pattern | Equivalence Confidence |
|------|---------|----------------------|
| LOG_STRING | Mutation in call to `logger.*`, `structlog.*`, `logging.*` where only a string literal changes | High |
| TYPE_ANNOTATION | Mutation in function signature type hints (`: str` → `: int`) | High |
| DEFAULT_STRUCTURAL | `.get("key", {})` → `.get("key", None)` where result is used as dict | Medium |
| UNUSED_RESULT | Mutation in line whose result is not assigned or passed to another call | Medium |
| DEBUG_ONLY | Mutation behind `if logger.isEnabledFor(DEBUG):` or similar guard | Medium |

### Alternatives Considered
- **Manual review of all 8,822**: Impractical at scale.
- **No equivalent detection**: Would produce artificial tests that test meaningless behavior differences.
- **Machine learning classification**: Over-engineered for a one-shot task.

## 4. Test Generation Strategy

### Decision
Generate targeted pytest test functions that assert on the specific behavior the mutation would alter. Each test is written in the existing test style: `from __future__ import annotations`, plain `test_` functions, no classes unless the existing test file uses them.

### Test Placement Rules
1. Find the corresponding test file at `tests/<mirror-path>/test_<module>.py`
2. If it exists, append the new test function(s) to the end of the file
3. If the test file doesn't exist, create it at the conventional location
4. If the entire test package directory doesn't exist, create it first

### Test Naming Convention
`test_kills_mutant_<N>_<short_description>` where `<N>` is the mutation ID number.

### Test Content Pattern
```python
def test_kills_mutant_33_validate_pack_active_rules_boundary():
    """Kills mutmut_33: > 0 changed to >= 0 in validator.validate_pack."""
    from specmetrics.plugins.rule_pack.validator import RulePackValidator
    # ... test that specifically exercises the > 0 boundary
```

### Alternatives Considered
- **Mutation-specific test framework**: Rejected — tests should use the same pytest patterns as the project.
- **Test-per-file approach**: Rejected — appending to existing test files keeps the test layout clean.

## 5. Lint & Test Commands

### Decision
Use the project's existing quality commands.

### Commands
```bash
ruff check .          # Lint
pytest tests/         # Full test suite
pytest tests/path/to/test_file.py::test_name  # Individual test
```

### Rationale
The constitution defines `ruff` for linting and `pytest` for testing.

## 6. Report Structure

### Decision
The Markdown report at `mutants/survivor-analysis.md` groups survivors by module, with per-survivor classification and rationale.

### Sections
1. **Summary**: Total survivors, guarded count, new-test count, equivalent count, skipped count
2. **Per-Module Sections**: Grouped by source module path
   - Survivor table: ID, source line, mutation description, classification, rationale
3. **Equivalent Mutants**: Grouped list for human review
4. **Test Files Modified**: List of files modified/created with survivor count

### Alternatives Considered
- **JSON report**: Less human-readable; rejected for the primary output (complementary JSON could be added later).
- **Per-survivor files**: Too many files (8,822); rejected.
